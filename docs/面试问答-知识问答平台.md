# 知识问答平台（FinRAG）

> 面向 PDF 与通用文档构建可检索、可追溯的 RAG 服务，覆盖文件解析、结构化切分、混合检索、重排序与流式问答链路。

## 介绍一下这个项目的整体架构和核心流程
1. 整体是一个 RAG（检索增强生成）服务，用 FastAPI 提供 HTTP 接口，核心链路是「文档入库」和「问答」两条。
2. 入库链路：上传文件 → PDF 用 Marker 解析成 Markdown → 按标题/段落/表格结构切分成子块 → 写入 Milvus 向量库 + SQLite FTS5 关键词索引。
3. 问答链路：用户提问 → 结合历史对话改写检索问句 → Milvus 向量召回 Top 40 → SQLite FTS5/BM25 关键词召回 Top 40 → RRF 融合 → BGE Reranker 重排序 → 按 parent_id 恢复完整连续记录 → 大模型基于上下文流式生成答案。
4. 存储层：MinIO 存原始文件与解析产物，MySQL + SQLAlchemy 存文档元数据和处理状态；Docker Compose 启动 Milvus、MinIO、etcd 等本地中间件。

## 为什么选择 RAG，RAG 解决什么问题
1. 大模型训练数据有截止时间，且无法覆盖用户自己的私有文档（年报、内部资料等），直接问会答错或编造。
2. RAG 的思路是「先检索、再生成」：把用户文档提前切块、向量化入库，问答时先检索出相关片段，再把这些片段作为上下文喂给大模型生成答案。
3. 好处：答案可追溯（有来源文档）、可增量更新（新文档入库即可）、减少幻觉（限制大模型只依据上下文回答）。

## 文档入库的整体流程详细介绍一下
1. 前端上传文件到 `POST /upload_file`，后端读取文件内容后加入 BackgroundTasks 后台异步处理，立即返回「上传成功，后台处理中」，避免长解析阻塞请求。
2. 把原始文件上传到 MinIO，拿到 `minio_url`。
3. 在 MySQL 建一条文件记录，状态置为 `1`（处理中）。
4. 判断扩展名是否 `.pdf`：非 PDF 直接标记失败/跳过解析；PDF 保存到本地临时目录 `tmp/{uid}/`。
5. 用独立子进程调用 `marker_parse.py` 把 PDF 解析成 Markdown（进程隔离，失败不影响主服务）。
6. 读取 Markdown，用 `split_md_content` 按标题/段落/表格结构切分成子块。
7. 子块批量写入 Milvus（HNSW/IP），写入成功的子块同步写入 SQLite FTS5 关键词索引。
8. 全部成功后更新状态为 `2`（成功），任何一步异常则更新为 `3`（失败）并记录日志。

## 为什么用 Marker 来解析 PDF，它和 PyPDF/OCR 有什么区别
1. Marker 是专门做 PDF→Markdown 的深度学习管线，能保留文档结构（标题、列表、表格、公式），输出结构化 Markdown。
2. 对比 `pypdf`/`PyPDF2`：它们只抽取文本流，会丢失标题层级、表格结构、阅读顺序，切分时无法按结构处理。
3. 对比纯 OCR（如 Tesseract）：OCR 面向扫描件，无版面结构，速度慢；Marker 对扫描件也支持 `force_ocr` 兜底，正常文档则走版面分析。
4. Marker 底层用 Surya 系列模型做版面分析、文字识别，支持多语言和图片提取配置，最终产物是可进一步结构化切分的 Markdown。

## 为什么 Marker 要用独立子进程来跑
1. Marker 要加载多个深度学习模型，内存/显存占用大，若和主服务同进程会常驻内存，解析完也无法释放。
2. 进程隔离保证稳定性：解析崩溃、OOM 或异常不会拖垮 FastAPI 主服务。
3. 主服务用 `subprocess.run` 调用 `marker_parse.py`，子进程把结果（ok、markdown_path、error、traceback）写成 JSON 文件，主服务读取判断成功/失败。

## 文本是怎么切分的，为什么按标题、段落和表格结构切
1. 先用正则识别 Markdown 标题（`#` 到 `#####`），维护当前标题栈，`section` 字段记录标题路径（用 ` / ` 拼接），这样每个片段都带着章节归属。
2. 识别表格：以 `|` 开头结尾、且下一行是分隔行的判定为表格，单独切分，保留表头信息。
3. 正文文本块再用 LangChain 的 `RecursiveCharacterTextSplitter` 二次切分，`chunk_size=500`、`chunk_overlap=50`，分隔符按 `\n\n → \n → 空格 → 字符` 从大到小递归切。
4. 按结构切的原因：表格如果被无脑按长度切开，行列语义会破坏；按标题切能让检索结果带上章节上下文，回答更完整、可追溯。

## 表格的跨页和连续表格是怎么处理的
1. 识别「表头行 + 分隔行」作为表格开始，读取后续连续的表格行。
2. Marker 跨页时可能省略重复表头、末尾列缺失，`_is_table_continuation_after_blank_line` 通过「首列为空但后续列有值 + 下一行是分隔行」等特征判断空行后仍是同一张表的续行，避免表格被拆散。
3. 处理重复表头：跨页重复出现的表头行会被识别并跳过。
4. 处理续行：某行首列为空表示是上一行的换行续写，会合并回上一行对应列（用 `\n` 拼接）。
5. 列数对齐：不足补空字符串，多余截断，保证每行列数一致。

## parent_id、chunk_index、chunk_count 是干什么的
1. 一个「记录」（一段正文或一个表格行）可能被 `RecursiveCharacterTextSplitter` 切成多个子块。
2. 同一记录的所有子块共享同一个 `parent_id`，并用 `chunk_index`（第几块）、`chunk_count`（共几块）标记顺序。
3. 作用：检索命中某个子块后，能按 `parent_id` 精确查询出这条记录的全部子块，按 `chunk_index` 排序还原完整连续内容，避免内容被 chunk 截断导致上下文丢失。
4. `parent_id` 是用 `sha256` 对「文档ID + 记录类型 + 章节 + 序号 + 内容」生成的稳定哈希，重复入库能得到一致标识。

## chunk_size 为什么选 500，overlap 有什么作用
1. 500 是一个经验平衡点：太小则单个片段信息不足、检索召回碎片化；太大则片段粒度粗、干扰信息多、超出 embedding 与 reranker 的有效长度。
2. `chunk_overlap=50` 让相邻块之间保留部分重叠，避免语义内容恰好被切断在块边界，检索时上下文更连续。
3. 配合 parent 记录恢复机制，即使单块只有 500，最终返回的是整条连续记录，兼顾「检索精度」和「回答完整」。

## 为什么用 Milvus 做向量检索，向量检索的原理
1. Milvus 是开源向量数据库，专为高维向量相似度检索设计，支持 HNSW 等近似最近邻（ANN）索引，适合大规模、低延迟的语义召回。
2. 原理：用 embedding 模型把文本编码成稠密向量，把「语义相似」转化为「向量距离近」；查询时把问题也编码成向量，在向量空间找距离最近的 Top K。
3. 本项目用 BGE-M3 生成 1024 维向量，索引用 HNSW，度量用内积 IP，配合向量归一化后等价于余弦相似度。

## HNSW 和 IP 度量、归一化具体是什么
1. HNSW 是一种基于图的近似最近邻索引，构建多层图，检索时从上层粗粒度逐步下沉到下层精搜，用较小精度损失换取数量级的加速。
2. 参数 `M=8`（每个节点在图里的最大连接数，越大越准但越占内存）、`efConstruction=64`（构建时搜索宽度）；检索时 `ef=max(64, top_k)` 控制召回质量。
3. 度量用 IP（内积）：embedding 编码时设置 `normalize_embeddings=True`，向量都归一化到单位长度后，内积就等于余弦相似度，检索快且稳定。

## 为什么 embedding 用 BGE-M3，维度为什么是 1024
1. BGE-M3 是多语言、多功能（dense + sparse + multi-vector）、多粒度的 embedding 模型，中英文效果都比较好，适合通用文档问答。
2. 它的 dense 向量输出维度是 1024，比常见的 768 表达空间更大。
3. 通过 `HuggingFaceEmbeddings` 本地加载（模型缓存在 `models/bge-m3`，用 ModelScope 下载），避免每次请求都走远程 embedding API。

## 为什么要做混合检索，向量检索和关键词检索各自的优缺点
1. 向量检索：语义相似，能召回「不同措辞但同义」的内容，但对精确关键词不敏感——型号、编号、日期、专有名词、代码等容易被语义相近但无关的内容干扰。
2. 关键词检索（BM25）：精确匹配词项，对实体、编号、专有名词召回准确，但无法处理同义词、改写、语义相近的内容。
3. 两者互补：向量管「意思对」，关键词管「字面对」，融合后兼顾语义查询与精确关键词查询。设计文档里的例子就是「比亚迪营业额」这种带具体数字/实体的问题，纯向量容易漏掉含 `602,315` 的精确片段。
4. **「互补」不是照本宣科，我端到端测过**：50 条稀有专名查询上，纯向量最终命中率只有 **0.320**，双路 **0.980**，其中 **33 条是关键词路单方面救回来的**。差距不是排序问题而是召回不到——单独测向量单路，`云辇`、`中冶瑞木`、`高管锁定` 这类词的 top-40 候选里，正文含该词的子块数是 **0**。密集检索把稀有专名压进通用语义空间是已知短板，我只是把它量化了。
5. **边界也要主动说**：这个评测集是稀有字面词的应力测试（查询=模板套用评测词，相关性=字符串包含），它证明的是**关键词路不可或缺**，**不能证明向量路的必要性**——这个评测集里不可能存在一条需要语义理解才能答对的查询。要证明向量路的价值，得另做一套「查询与答案无字面重叠」的释义类查询，这一步我还没做。不主动交代这一点，被追问时就是硬伤。

## SQLite FTS5 / BM25 是什么，中文是怎么分词的
1. SQLite FTS5 是 SQLite 内置的全文检索虚拟表，支持 `bm25()` 排序函数，天然给出 BM25 相关度评分。
2. 本项目用通用分词：英文/数字/下划线的连续串作为一个词元；中文因为没有天然空格，用二元词（bigram），即每两个连续汉字切一个词元，单字也保留。
3. 不依赖 jieba 等分词词典，保持「领域无关」——项目约定不允许为年报、财务等特定实体硬编码词典。代价是「云辇」「丹拿」这类未登录专有名词会被 jieba 切成单字，而 bigram 能完整保留。
4. 查询用 `OR` 连接各词元去 `MATCH`，排序交给 `bm25(keyword_fts)`，取 Top 40。
5. **这里不能用 `AND`，我踩过坑**：bigram 必然切出跨词边界的噪声词元（「的营」「入是」），要求全部命中会让自然语言长查询恒返回 0。更麻烦的是它**静默**——FTS5 返回空列表而不抛异常，`retriever` 里的降级分支不会触发、没有告警，融合阶段对空列表退化成恒等变换。结果就是「双路召回 + RRF 融合」实际一直是单路向量检索在跑，而且没人发现。改成 `OR` 语义后自然语言查询召回从 0 恢复到 40。
6. 查询侧再做一层**文档频率剪枝**：文档频率超过语料子块总数 2% 的词元（如「情况」1837/8103、「比亚」1477/8103）区分度极低，直接丢弃，避免它们在 BM25 累加打分中淹没稀有的信号词元。阈值完全取自语料自身的统计量，不依赖任何领域词表。

## RRF 是什么，为什么用 RRF 而不是直接比较分数
1. RRF（Reciprocal Rank Fusion，倒数排名融合）：`score = Σ 1/(k + rank)`，k 取 60，只基于每条结果在各路里的排名计算融合分。
2. 原因：向量召回的打分（内积/余弦相似度）和 BM25 的打分（词频统计）尺度完全不同，不能直接相加或归一化后比较；RRF 只看排名不看分数绝对值，天然适合融合异构检索结果。
3. 实现：向量 Top 40 和关键词 Top 40 各自排名，按 `parent_id:chunk_index` 去重，同一结果在不同路得分累加，得到候选集（最多 80 条）。
4. **定位要说清楚**：候选集随后交给交叉编码器统一精排，最终顺序完全由 Reranker 决定，RRF 的顺序不进入最终结果。所以 RRF 在本项目里的实际作用是「合并两路候选 + 去重」——**两路贡献的是召回率，排序由 Reranker 一力承担**。这一点很容易被追问「既然要用 Reranker 重排，为什么还要 RRF」，答案就是：RRF 解决的是异构结果**怎么合并成一个候选集**，不是最终排序。

## 为什么还要加 Reranker，交叉编码器和双编码器有什么区别
1. 召回阶段用的是双编码器（bi-encoder）：query 和 doc 被独立编码成向量再算相似度，速度快、可离线建索引，但 query 和 doc 之间没有充分交互，精度有限。
2. Reranker 用交叉编码器（cross-encoder）：把 `query + doc` 拼接成一个输入送进模型，两者深度交互后输出相关性分数，精度高但慢，所以只对融合后的小候选集（约 80 条）重排。
3. 本项目用 `bge-reranker-base`，`logits` 作为重排分数，从融合候选里再筛出最相关的，兼顾「召回阶段的快」和「精排阶段的准」。

## 为什么要做查询改写
1. 多轮对话里用户的问题常带指代（「这个」「上述」「原文」「全文」）或省略主语，直接拿原句去检索会召不回正确内容。
2. rewrite 节点把历史对话 + 当前问题交给 LLM，让它生成一条「完整、自包含」的检索问句。
3. 改写规则：补全指代、保留历史和当前问题里的实体/机构/文档名/时间/业务术语、不编造历史没有的事实、只输出改写后的问句。

## LangGraph 是怎么组织这个工作流的
1. 用 LangGraph 的 `StateGraph` 定义三个节点和边：`START → rewrite → retriever → generator → END`。
2. 节点间共享一个 `AgentState`（query、standard_query、documents、answer、history_str），每个节点读 state、返回要更新的字段。
3. 好处：状态显式、图结构清晰，后续可以方便地加条件分支、循环、多节点；且 `astream_events` 能拿到每个节点的流式事件，方便做 SSE。

## SSE 流式问答是怎么实现的
1. LLM 用 `ChatOpenAI(..., streaming=True)` 开启流式。
2. 通过 `graph.astream_events(state, version="v2")` 订阅 `on_chat_model_stream` 事件，只保留 `generator` 节点的流式 chunk（避免把改写等中间过程的 token 也吐给前端）。
3. 每个 chunk 封装成 `data: {"content": ..., "role": "assistant", "type": "Normal"}\n\n` 的 SSE 格式 yield 出去，最后再 yield 一条 `type: "End"` 表示结束。
4. 外层用 `StreamingResponse(media_type="text/event-stream")` 返回，前端拿到后逐字渲染。

## 会话上下文（多轮对话历史）是怎么管理的
1. 服务内维护一个内存字典 `_store`，按 `conversation_id` 存对话历史，没传 `conversation_id` 就生成一个 UUID。
2. 每次请求取最近 10 条历史，拼成 `role:content` 的 `history_str`，传给 rewrite 节点用于改写。
3. 请求结束（`finally`）时把本轮 user 和 assistant 的内容追加回历史，保证下一轮能拿到完整上下文。
4. 当前是内存存储，服务重启会丢失；这也是一个可以进一步优化的点（可换成 Redis）。

## 如何防止大模型幻觉
1. 生成 prompt 明确要求「仅依据检索到的知识库上下文回答，不得编造上下文不支持的事实」。
2. 回答后要求给出「依据与来源」部分，列出支撑要点。
3. 当没有检索到有效上下文时，走另一条「通用回答」路径：明确告诉用户「未检索到参考内容」，并直接基于通用知识回答，但「不声称参考了文档、不提供未给出的来源」。

## 关键词索引不可用或失败时怎么降级
1. `retriever.search` 里关键词检索包在 `try/except` 里，一旦 FTS5 查询失败或索引不可用，捕获异常、记日志，把 `keyword_docs` 置空。
2. 这样就自动降级为「仅向量检索」，整个问答链路不断，只是少了一路召回。

## 入库的可靠性做了哪些保障
1. Milvus 批量写入（`batch_size=256`）失败时，`_insert_batch_with_fallback` 降级为逐条写入；单条仍失败则跳过该条并记录，不阻塞整体入库。
2. 入库前校验元数据长度（source、section、document_id、parent_id 等），超长的 chunk 直接跳过，避免写库报错。
3. 写入 Milvus 成功的子块才同步写入关键词索引，保证两路索引一致。
4. 关键词索引按 `document_id + parent_id + chunk_index` 稳定键覆盖写入，重复入库会替换旧记录而不是产生重复。
5. 父记录精确查询失败时，降级为「保留命中的原始子块」，不影响返回。

## 元数据过滤是怎么做的
1. `/search` 支持 `source` 和 `filters`（JSON metadata 的精确等值过滤）。
2. 构造 Milvus 过滤表达式：`source == "..." and metadata["key"] == value`。
3. 做了严格校验防止注入：字段名必须是合法 Python 标识符，值只允许字符串/数字/布尔，非有限浮点拒绝。

## 关键词索引的历史数据是怎么重建的
1. 升级后已有的 Milvus 数据不会自动出现在 FTS5 索引里，提供 `scripts/rebuild_bm25_index.py` 全量重建。
2. 用 Milvus 的 `query_iterator` 分批（默认每页 500）遍历全部子块，写入一个**临时** SQLite 文件。
3. 所有分页成功后用 `os.replace` 原子替换正式索引；中途失败则删除临时文件、保留旧索引，保证不会出现半成品索引。
4. 词元文档频率统计（查询侧剪枝的依据）在写入时增量维护，重建时随索引一并生成；覆盖写入同一子块会先撤销旧文本的贡献，否则反复覆盖会让频率单调上涨、剪枝阈值失真。
5. 引入剪枝之前建立的索引没有统计表，剪枝会**静默失效**（检索仍可用，只是退化成朴素 bigram）。检索日志会显式告警而不是默默降级；补齐统计不需要访问 Milvus，`scripts/backfill_token_statistics.py` 直接从索引里已存的子块文本重新推导，秒级完成。

## 你怎么证明关键词切分策略是合理的
1. 做了**受控对比实验**：同一份语料、同一个 SQLite FTS5/BM25 实现、同样的 `top_k=40`，只替换分词器，所以指标差异完全归因于切分策略，而不是 BM25 实现或语料差异。
2. 评测集不依赖人工标注，也不依赖领域词表：候选词由语料自动挖掘（jieba 切得开、但左右两半互相强预测的组合，即共现粘性 ≥ 0.6），相关性判定用「原文是否包含该词」这个客观标准。
3. **关键结论：朴素 bigram 不如 jieba**（MRR 0.863 vs 0.899）——我原本的假设被自己的数据推翻了。根因是 bigram 对文档侧友好（不漏词），对查询侧有害：一条长查询会切出 1 个信号词元加 9 个噪声词元，而 BM25 是累加打分，噪声靠数量压过信号。
4. 改进后 **bigram + 查询侧文档频率剪枝** 在两端语料上全面超过 jieba：

| 语料 | 策略 | Hit@40 | Recall@40 | MRR@10 |
|---|---|---|---|---|
| 训练集 2022+2023（8103 子块） | 朴素 bigram | 0.980 | 0.907 | 0.863 |
| | jieba | 1.000 | 0.958 | 0.899 |
| | **bigram + 剪枝** | 0.980 | 0.943 | **0.943** |
| 留出集 2024（4908 子块） | 朴素 bigram | 0.940 | 0.785 | 0.368 |
| | jieba | 0.820 | 0.675 | 0.365 |
| | **bigram + 剪枝** | 1.000 | 0.903 | **0.583** |

5. 留出集用训练集选定的 2% 阈值，**不重新调参**，所以不是过拟合；而且 2% 和 5% 的指标完全一致，说明参数不敏感。

> 追问应对：这个评测有什么局限？——必须主动交代：① 评测集限制相关集 ≤40 个子块，因此**文档频率本来就高的词条从未被评测**，而这恰恰是剪枝唯一可能有害的场景，结论对这类查询没有覆盖；② 相关性用字符串包含判定，天然偏向字面匹配，对纯语义改写类查询不公平；③ 端到端验证已经补上（双路 0.980 vs 纯向量 0.320，33 条靠关键词路救回），但那个评测集是稀有字面词的应力测试，**它证明了关键词路不可或缺，却不能证明向量路的必要性**——该评测集里不可能出现需要语义理解才能答对的查询，释义类查询尚未覆盖；④ 语料集中在比亚迪年报一类文档上。这些都在 `docs/混合检索-关键词切分策略评测.md` 里写明了。

## 性能上做了哪些优化
1. 单例复用：embedding 模型、Milvus vector store、关键词索引都只加载一次，避免每个请求重复加载模型。
2. 文件解析用 BackgroundTasks 后台异步执行，上传接口立即返回。
3. Milvus 批量写入 + 失败逐条降级。
4. `@time_consume` 装饰器统一计时（并修复了异步函数被同步装饰器包装后只记录协程创建时间的问题），方便定位耗时瓶颈。

## 为什么文件用 MinIO、元数据用 MySQL
1. MinIO 是 S3 兼容的对象存储，存原始上传文件（PDF）和解析产物（Markdown），本地用 Docker 起，上传下载都走流式。
2. MySQL + SQLAlchemy 只存轻量元数据（文件 ID、名称、大小、状态、minio_url），通过 `pool_pre_ping`、`pool_recycle` 保持连接健康。
3. 职责分离：大文件二进制放对象存储，可检索的元数据放关系库，用 `minio_url` 关联。

# 原理深挖（面试追问层）

## HNSW 的原理详细讲一下
1. **是什么**：HNSW（Hierarchical Navigable Small World）是一种基于「多层图」的近似最近邻（ANN）索引，用来在向量库里快速找到和 query 最像的 Top K，不必和每一条都算一遍距离。
2. **图的构建**：把每个向量当成一个节点，用「小世界」结构连边——任意两个节点之间跳数很少（类似社交网络的六度分隔）。整个图分多层：最底层（layer 0）包含全部节点，越往上节点越稀疏；每个节点被放到第 l 层的概率按指数衰减，所以层数呈对数分布，节点数越多层也不会无限长。
3. **检索流程**：
   - 从最顶层的入口点开始，在当前层做贪心下降，找离 query 最近的点，直到局部最优；
   - 下降一层，以上一层找到的最近点作为新入口继续贪心；
   - 一路降到 layer 0，用一个大小为 `ef` 的候选集合（小顶堆）维护「当前最接近的候选」，最终返回 Top K。
4. **三个关键参数**：
   - `M`：每个节点最大连接数，越大图越密、召回率越高，但内存和构建时间增加（本项目 `M=8`）；
   - `efConstruction`：建索引时的搜索宽度，越大图质量越高但构建越慢（本项目 `efConstruction=64`，偏保守、构建快）；
   - `ef`（查询时）：查询候选集合大小，越大召回越准但查询越慢（本项目 `ef=max(64, top_k)`）。
5. **为什么用近似而不是暴力全量**：全量算内积/余弦复杂度是 O(N·D)（N 是文档数、D=1024），规模一大就扛不住；HNSW 靠图遍历把复杂度压到接近 O(log N) 量级，用一点点精度损失换数量级的加速，召回率通过 `ef` 调节。

> 追问应对：HNSW 和 IVF-Flat/IVF-PQ 的区别？——HNSW 是图索引，召回率通常更高但内存占用大、无需训练；IVF 是基于聚类的倒排索引，内存省但召回略低、通常要先聚类训练。为什么 `M=8`？——经验默认值，是召回率和内存的平衡点。

## RRF 的原理详细讲一下
1. **公式**：`score(d) = Σ_{r∈R} 1 / (k + rank_r(d))`，`d` 是文档，`R` 是各路检索器，`rank_r(d)` 是 d 在第 r 路结果里的排名（从 1 开始），`k` 是常数（本项目 `RRF_K=60`）。
2. **直觉**：`1/(k+rank)` 是递减函数，排名越靠前权重越高，但差距是递减的（第 1 名和第 2 名的分差，远大于第 39 名和第 40 名）。它只建模「排名」，不建模「分数绝对值」。
3. **为什么不能用分数直接相加**：向量召回的分（内积/余弦，可能几十上百）和 BM25 的分（词频统计，可能几到几十）量纲完全不同，直接相加会让某一方主导、另一方形同虚设；即便做 min-max 归一化，也依赖「每路分数分布」的假设，而分数分布随 query 变化，不稳定。
4. **为什么用排名而不是分数**：排名在不同检索器之间是「可比」的（任何一路里「第 1 名 vs 第 5 名」含义一致），而原始分数不可比；同时 RRF 对某一路的异常高分鲁棒，不会因为某一路冒出个离谱高分就压过一切。
5. **为什么 k 取 60**：k 是平滑参数，控制排名对最终分的影响陡峭度，k 越大、高排名和低排名差距越小越「平滑」；60 是 Cormack 等人提出 RRF 时的论文经验默认值，被广泛采用。
6. **本项目实现**：向量 Top 40（排名 1..40）和关键词 Top 40（排名 1..40）各自带排名，按 `parent_id:chunk_index` 去重，同一 chunk 在两路都命中则分数累加，按融合分降序得到候选集（最多 80），交给 Reranker 精排。注意融合分**只用于构造候选集**：Reranker 对这 ≤80 条全量重排、不截断，因此 RRF 的顺序不影响最终结果——它保证的是「两路的好结果都进得来」，而不是「谁排在前面」。

> 追问应对：RRF 相比 learning-to-rank / 加权求和？——RRF 无需训练、无需调权重、稳定；但无法针对具体业务优化权重。如果两路返回同一批结果？——去重后累加分数，同一文档排名越靠前越占优，自然增强置信度。k 能调吗？——能，k 越小越看重头部排名，k 越大越「民主」。

## 交叉编码器（Reranker）和双编码器（Embedding）的原理区别
1. **双编码器（bi-encoder，如 BGE-M3）**：query 和 doc 分别编码成向量，再算内积/余弦。两者在编码阶段互不相见、无交互，所以可以离线把海量 doc 预先向量化入库，检索极快；代价是「query 和 doc 的细粒度语义匹配」能力弱。
2. **交叉编码器（cross-encoder，如 bge-reranker-base）**：把 `query + doc` 拼接成一个输入送进 Transformer，两者在每一层都做 attention 交互，输出一个相关性 logits。精度显著更高，但每对都要过一遍模型、无法离线索引，所以只能用于小候选集。
3. **两段式流水线**：召回阶段用双编码器从全库快速捞出候选（本项目 40+40 → 融合后约 80 条），精排阶段用交叉编码器对这几十条做深度打分排序。这样兼顾「召回快」和「精排准」。
4. **为什么 Reranker 输入截断到 512**：交叉编码器拼接 query 和 doc 后 token 数有限制，`max_length=512` 截断，所以 chunk 不能太长，这也是 chunk_size 设 500 的另一个原因。
