# 关键词切分策略评测：bigram 与 jieba 的受控对比

本文记录混合检索中关键词一路的分词策略选型过程、实验方法、结论与局限。所有数字都可由 `scripts/` 下的脚本复现。

## 1. 要回答的问题

关键词一路最初采用二元切分（bigram，每两个连续汉字一个词元），理由是「领域无关、不依赖词典」，并且预期它比 jieba 更适合含大量专有名词的年报语料。**这个预期需要用数据验证，而不是靠直觉。** 本评测要回答三件事：

1. 朴素 bigram 是否真的优于 jieba？
2. 如果不然，bigram 的问题出在哪一环？
3. 能否在不引入领域词表的前提下修掉它？

## 2. 实验设计

**受控变量**：同一份语料、同一个 SQLite FTS5/BM25 实现、同样的 `top_k=40`，**只替换分词器**。因此指标差异完全归因于切分策略，而不是 BM25 实现差异或语料差异。

各策略只体现为 `KeywordIndex` 的一组构造参数，评测与线上共用同一份实现：

| 策略 | 构造参数 |
|---|---|
| 朴素 bigram | `tokenizer=tokenize, max_document_ratio=None` |
| jieba | `tokenizer=jieba_tokenize, max_document_ratio=None` |
| bigram 文档 + jieba 查询 | `tokenizer=tokenize, query_tokenizer=jieba_tokenize` |
| bigram + 查询侧剪枝 | `tokenizer=tokenize, max_document_ratio=0.02` |

**为什么必须共用实现**：剪枝逻辑一度在评测脚本里独立实现了一份，生产代码里是另一份。两份实现迟早漂移，而本项目已经因为「两处逻辑不一致且静默失败」出过一次事故（见 §6）。现在评测直接调用生产代码，不存在第二份实现。

## 3. 评测集构造

评测集**不使用人工标注，也不使用任何领域词表**——项目约定禁止为年报、财务指标或特定实体硬编码词典，所以标注本身也不能依赖领域知识。

### 3.1 候选词自动挖掘

目标是找出「jieba 切不开、但确实是固定搭配」的词。判据是**共现粘性**：

```
候选词 = 左右两半互相强预测的相邻词对
粘性   = min(词对频次 / 左半频次, 词对频次 / 右半频次) ≥ 0.6
约束   = jieba.lcut(整词) 长度 ≥ 2（说明它不在 jieba 词典里）
```

粘性这个判据的好处是**不需要停用词表**：「的」随处出现，与任何词的共现比例都极低，会被自动排除。挖出的词如：云辇、刀片电池、方程豹、硫酸雾、慈善基金会。

### 3.2 相关性判定

对每个评测词 T，**相关子块 = 正文包含 T 的全部子块**。判定标准是客观的字符串包含，可复现、无需人工判断。

限制相关集规模 ≤ 40（与 `KEYWORD_CANDIDATE_COUNT = 40` 对齐），否则 Recall@40 在理论上无法取到 1.0，指标不可解释。

### 3.3 为什么不用大模型生成查询

用 LLM 生成评测查询会**复述原文措辞**，从而抬高关键词检索的成绩（关键词检索靠的就是字面匹配），评测会系统性偏向被验证的一方。因此查询统一用四个固定模板套用评测词：

```
{term}的具体情况是怎样的 / 关于{term}的说明有哪些
报告中提到的{term}是什么 / {term}相关的数据情况如何
```

### 3.4 指标

- **Hit@40**：top-40 里至少命中一个相关子块的查询占比
- **Recall@40**：top-40 覆盖了多少比例的相关子块
- **MRR@10**：第一个相关子块排名的倒数均值，衡量「相关结果排得够不够前」

## 4. 结果

### 4.1 训练集：2022 + 2023 年报，8103 个子块，50 个评测词

| 策略 | Hit@40 | Recall@40 | MRR@10 |
|---|---:|---:|---:|
| 朴素 bigram | 0.980 | 0.907 | 0.863 |
| jieba | 1.000 | 0.958 | 0.899 |
| bigram 文档 + jieba 查询 | 0.860 | 0.743 | 0.625 |
| **bigram + 查询侧剪枝 2%** | 0.980 | 0.943 | **0.943** |
| **bigram + 查询侧剪枝 5%** | 0.980 | 0.943 | **0.943** |

### 4.2 留出集：2024 年报，4908 个子块

阈值**固定为训练集选定的 2%，不重新调参**，用于排除过拟合：

| 策略 | Hit@40 | Recall@40 | MRR@10 |
|---|---:|---:|---:|
| 朴素 bigram | 0.940 | 0.785 | 0.368 |
| jieba | 0.820 | 0.675 | 0.365 |
| **bigram + 查询侧剪枝 2%** | 1.000 | 0.903 | **0.583** |

## 5. 结论

**5.1 朴素 bigram 不如 jieba。** 训练集上 MRR 0.863 vs 0.899，原始假设被数据推翻。

**5.2 问题出在查询侧，不在文档侧。** bigram 对文档侧是好事——它不漏词，`云辇` 这类未登录专有名词能完整保留。但对查询侧有害：一条自然语言长查询会切出大量跨词边界的噪声词元。以「比亚迪2023年的营业收入是多少」为例，11 个词元里只有少数是信号，其余是「年的」「入是」「是多」这类跨词边界碎片。BM25 是**累加**打分，噪声靠数量压过信号——目标子块被挤到第 88、326、411 位，远在 top-40 之外。

**5.3 查询侧按文档频率剪枝可以修掉它，且不需要词典。** 丢弃文档频率超过语料子块总数 2% 的词元。这些词元在语料中无处不在、区分度趋近于零：

| 词元 | 文档频率 / 8103 |
|---|---:|
| `公司` | 3477 |
| `情况` | 1837 |
| `比亚` | 1477 |
| … | |
| `腾势` | 43 |
| `刀片` | 18 |
| `云辇` | 11 |

阈值完全取自**语料自身的统计量**，与领域无关。

**5.4 剪枝后 bigram 全面超过 jieba**，且在留出集上优势更大（MRR 0.583 vs 0.365）。留出集上朴素 bigram 反而赢过 jieba（0.368 vs 0.365），说明 jieba 在训练集上的领先部分来自词典覆盖的运气——留出集的词（`下水道水质标准`、`氮氧化`、`llc直接`）更碎。

**5.5 参数不敏感。** 2% 与 5% 指标完全一致，说明这不是精调出来的结果。

**5.6 一个失败的尝试值得记录**：「bigram 文档 + jieba 查询」设想是「文档侧放宽召回、查询侧收紧噪声」，结果最差（MRR 0.625）。原因是**词元空间不对齐**：jieba 会把未登录词切成单字（`云辇`→`云`/`辇`），而 bigram 索引里根本不存在单字词元，查询词元在索引里永远匹配不到。这条负结果说明：文档侧和查询侧的分词器必须产生同一个词元空间。

## 6. 局限（必须主动交代）

1. **评测集系统性偏袒剪枝。** 相关集规模被限制在 ≤40 个子块，因此**文档频率本来就高的词条从未进入评测**——而这恰恰是剪枝唯一可能有害的场景。结论对「查询词本身就是高频词」的这类查询没有覆盖。
2. **剪枝存在退化情形。** 当一条查询的高区分度词元被整批剪掉、只剩下零星碎片时，查询会退化。以「比亚迪2023年的营业收入是多少」为例，剪枝后保留的是 `年的`/`的营`/`入是`/`是多`，语义上有意义的 `比亚`/`营业`/`收入` 全被剪掉——因为在这份语料里它们文档频率高达 18%，区分度确实接近零，但这也意味着查询只剩字面碎片信号。**代码里有两处防护**：小语料上比例阈值会退化成个位数，故设了绝对下限（10 个子块）；若词元被全部剪空则退回未剪枝词元。但「只剩零星碎片」这种情形两处防护都覆盖不到。聚合指标支持这个设计，单条查询则可能变坏。
3. **相关性判定偏向字面匹配。** 「原文包含该词」这个标准天然有利于关键词检索，对纯语义改写类查询不公平——而这类查询本该由向量一路负责。
4. **只测了关键词单路。** 本评测测的是关键词一路的召回指标，**没有端到端验证对最终回答质量的影响**。真实链路是「两路召回 → 合并去重 → 交叉编码器统一重排」，剪枝提升的是进入候选集的机会，方向正确，但 2% 对最终链路是否最优并未验证。
5. **语料单一。** 全部来自比亚迪年报（2022/2023/2024），结论对其他文档类型的迁移性未验证。

## 7. 生产落地

剪枝是生产代码的默认查询路径（`KeywordIndex` 的 `max_document_ratio` 默认 0.02）。词元文档频率在 `upsert_documents` 时增量维护，覆盖写入同一子块会先撤销旧文本的贡献。

**引入剪枝之前建立的索引没有统计表，剪枝会静默失效**（检索仍可用，只是退化成朴素 bigram）。这种情况检索日志会显式告警，而不是默默降级——「静默退化」正是本项目已经踩过的坑。补齐统计不需要访问 Milvus：

```powershell
python scripts/backfill_token_statistics.py
```

统计量完全由索引里已存的子块文本推导，秒级完成。

## 8. 复现

```powershell
# 训练集对比（语料取自 data/keyword_index.db）
python scripts/eval_tokenizer.py --work-dir <输出目录> --top-k 40 --mrr-depth 10

# 留出集验证（2024 年报，阈值固定 2% 不重新调参）
python scripts/eval_heldout.py --work-dir <输出目录> --top-k 40 --mrr-depth 10
```

依赖：`jieba`（仅评测脚本使用，用于 jieba 基线与候选词挖掘；生产检索链路不依赖它）。

**可复现性说明**：候选词排序曾只按频次排序，而语料统计用了字符串集合，集合迭代顺序随进程的哈希种子变化，导致同频词条的顺序在两次运行间漂移、评测集随之变化、指标无法复现（三次运行得到 0.873 / 0.906 / 0.880 三个不同的 bigram MRR）。现已显式指定排序次键并固定语料读取顺序，两次运行结果逐位一致。

> 注意：Windows 上 `--work-dir` 需用原生路径（如 `D:\code\FinRAG\tmp-eval`）。在 Git Bash 里传 `/tmp/...` 会被转换成 Windows 路径，与脚本内部拼接的字符串不一致。
